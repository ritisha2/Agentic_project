ESP-PMM Knowledge Base Architecture & Implementation Design
Document type: Detailed technical design / implementation specification  
Project: ADVAIT ESP Asset Performance Monitoring & Management (ESP-PMM) — Agentic Knowledge Layer  
Scope: Knowledge Base, ingestion, classification, storage, retrieval, evidence, Agent integration, runtime APIs, governance, security, evaluation and implementation  
Current ownership boundary: ESP predictive models are owned by another team; the Agentic layer is owned by the project user. The Agentic layer uses an LLM. The predictive-model stack does not require an LLM.
1. Executive Definition
The ESP-PMM Knowledge Base (KB) is not a single vector database containing PDFs. It is a governed knowledge subsystem that stores and retrieves relatively stable domain knowledge, procedures, model semantics, terminology, engineering references, operational playbooks and provenance metadata.
Dynamic operational facts must remain outside the KB as authoritative runtime data. Current asset identity/configuration should come from the Advait/client platform through an Asset API. Live/historical telemetry should come from the simulator during development and from the production asset/telemetry APIs in production. Current anomaly/fault/failure/rule outputs should come from the ESP AI Model team's runtime/API.
The intended Agent architecture is therefore:
```text
STATIC KNOWLEDGE
   -> Knowledge Ingestion
   -> Classification
   -> Structured / Graph / Object / Vector Stores
   -> Retrieval + Reranking
   -> Evidence Pack
DYNAMIC RUNTIME INFORMATION
   -> Asset API
   -> Telemetry API
   -> History API
   -> Model Output API
   -> Alerts / Events API
   -> Calculation / Feature APIs
STATIC EVIDENCE + RUNTIME EVIDENCE
   -> Evidence Pack
   -> Context Builder
   -> LLM
   -> Agentic Response
The ESP-PMM working draft explicitly separates the Asset Model, Feature Store, Model Runtime and AI Assistant; it specifies a RAG assistant using retriever + tool calling + evidence cards; and it describes the assistant as an evidence-backed operational copilot that should Observe, Diagnose, Explain, Recommend and Document.## 2. What the source deck explicitly requiresThe ESP-PMM deck states:- Equipment domain → data model → AI advisor.- The backend must preserve raw evidence while publishing clean features for models and assistant reasoning.- Architecture: OT/SCADA → Asset Model → Feature Store → Model Runtime → AI Assistant.- The AI Assistant uses retrieval + tool calling + evidence cards.- The assistant is an evidence-backed operational copilot, not a generic chatbot.- It should Observe: asset state, data quality, recent trends and active exceptions.- It should Diagnose: multi-signal patterns, likely failure modes and confidence.- It should Explain: tag movements, calculations, design envelope and source procedure.- It should Recommend: monitor, adjust, inspect, escalate or plan intervention.- It should Document: shift notes, exception reports and model-feedback labels.- Every answer should include confidence, evidence and escalation criteria.- The assistant must never invent missing sensor values, recommend unsafe speed changes without constraints, suppress alarms, hide uncertainty/source evidence, or override procedures.- The assistant must state confidence/data quality, link recommendations to tags/calculations, offer escalation, create an audit trail, and support human approval.Source reference: ESP-PMM Working Draft, especially pages 14, 16, 18, 19 and 23.## 3. Scope and Responsibility Boundary### 3.1 Other team: ESP AI Model TeamThe other team owns:- Rule Engine.- Anomaly Detection.- Failure Prediction.- Fault Classification.- Their training pipeline.- Their model artifacts/runtime.- Their model-specific feature engineering.- Their model evaluation.You do **not** need to load or call their Python/XGBoost/LSTM/etc. directly.Your system should treat them as a black-box model service with a versioned contract.### 3.2 Your responsibility: Agentic LayerYour system owns:- Knowledge acquisition.- Knowledge ingestion.- Knowledge classification.- Knowledge storage.- Retrieval.- Reranking.- Evidence Pack.- Context Builder.- Agent objectives.- Tool registry.- Tool calling.- LLM orchestration.- Grounding/citation.- Safety policies.- Runtime integration with asset/telemetry/model APIs.- Agent evaluation.- Agent UI integration.- Auditability.### 3.3 External source of truthThe Advait/client platform should remain authoritative for:- Asset identity.- Asset registration.- Client-specific asset metadata.- Active/inactive status.- Well/ESP configuration.- Client naming.- Installed equipment configuration.Do not create a competing authoritative asset registry in the KB.A local asset cache/projection is acceptable for performance and integration, but it is not the system of record and it is not the Knowledge Base.## 4. 12. Context Builder
The Context Builder should:
Receive user question and Agent objective.
Receive asset identity.
Receive Evidence Pack.
Apply tenant permissions.
Remove irrelevant evidence.
Apply source precedence.
Mark stale/missing inputs.
Attach citations/provenance.
Include model-output semantics.
Format a compact context for the LLM.
Example context:
```text
OBJECTIVE:
Explain active alert.
ASSET:
ESP-007, Well-045.
CURRENT DATA:
Motor temp 155 C
Flow 2180 BPD
Frequency 52 Hz
MODEL:
Anomaly 0.91
Fault Motor overheating, confidence 0.87
24h failure risk 0.31
ALERT:
MOTOR_TEMP_MARGIN_LOW, WARNING
KNOWLEDGE:
ESP thermal troubleshooting guidance, Manual p.12
CONSTRAINT:
Do not issue autonomous control action.
REQUIRED RESPONSE:
Explain cause, evidence, confidence and escalation.

## 29. Final Engineering DecisionsThe following decisions should be treated as the baseline specification:1. The Advait/client platform remains authoritative for client-specific asset registration.2. The Asset Registry is not a RAG KB.3. A local asset cache/projection is allowed but is not the source of truth.4. Live telemetry is fetched through APIs/tools.5. Historical telemetry is fetched through APIs/tools.6. ESP predictive models are owned by the other team.7. The Agent consumes model outputs through a stable adapter/API/event interface.8. The LLM is used in the Agentic layer.9. Static engineering/domain knowledge is stored in the KB.10. Dynamic operational facts are not treated as static KB truth.11. The previous project's layered KB architecture remains the foundation.12. Evidence Pack remains the critical bridge to the LLM.13. Knowledge retrieval uses exact/structured/graph/semantic approaches according to information type.14. Reranking happens before Evidence Pack construction.15. Context Builder controls what the LLM sees.16. Tenant isolation is enforced before retrieval and tool execution.17. High-impact knowledge is versioned and approved.18. Model semantics are explicitly documented so the LLM does not infer meaning from numbers alone.19. No autonomous equipment control is exposed to the LLM.20. Every operational answer must be traceable, uncertainty-aware and evidence-backed.## 30. 31. Source Alignment Note
The ESP-PMM working draft is the source of truth for the ESP-specific responsibilities and safety requirements used in this design. In particular, the deck's architecture separates Model Runtime from the AI Assistant, calls for RAG + tool calling + evidence cards, requires an evidence-backed operational copilot, and specifies confidence/evidence/escalation and human accountability.
