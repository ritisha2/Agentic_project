# 2. First: determine what the `.db` actually is

Do **not** immediately convert it.

A `.db` extension does not tell us whether it is:

* SQLite
* another embedded database
* a custom database export

First inspect:

```text
database type
tables
columns
indexes
row counts
timestamps
asset/well IDs
tag IDs
units

quality fields
```

For a historian, we specifically want something resembling:

```text

timestamp
tag_id / signal
value
unit
quality
source
```

or a wide schema such as:

```text
timestamp
asset_id
liquid_rate
pip
pdp
motor_current
motor_temperature
frequency
...
```

### The most important question

Does the `.db` contain **timestamped historical measurements**, or is it merely a static dataset?

If it contains time-stamped measurements, it can serve as your historian source.

# 4. Why time-series storage?

Yes, **this data should be treated as time-series data** if it is historical telemetry.

Typical characteristics:

```text
asset + signal + timestamp + value
```

Examples:

```text
FS-031 | liquid_rate       | 2026-08-31 10:00 | 956.4 BPD
FS-031 | intake_pressure   | 2026-08-31 10:00 | 237.1 psi
FS-031 | motor_temperature | 2026-08-31 10:00 | 100.2 C
```

That supports:

```text
6-hour trend
24-hour trend
7-day trend
30-day trend
before/after event
rolling averages
rate of change
forecast features
anomaly detection
```

Which is exactly what the guideline requires from `historian.get_window(...)`.

# 7. Historian REST API

Implement a dedicated service, for example:

```text
GET /api/v1/historian/{asset_id}/window
```

Parameters:

```text
start_time
end_time
tags/signals
aggregation
interval
```

Example:

```http
GET /api/v1/historian/FS-031/window
    ?start=2026-08-31T08:00:00
    &end=2026-08-31T14:00:00
    &signals=liquid_rate,intake_pressure,discharge_pressure,motor_temperature
    &aggregation=5m
```

Response:

```json
{
  "asset_id": "FS-031",
  "start_time": "...",
  "end_time": "...",
  "coverage": 0.98,
  "series": [
    {
      "signal": "liquid_rate",
      "unit": "BPD",
      "quality": "GOOD",
      "points": [
        {
          "timestamp": "...",
          "value": 956.4
        }
      ]
    }
  ]
}
```

This maps directly to the guideline's historian contract: tags + start/end + aggregation → timestamped values + quality + coverage.

This is important.

```json
  "status": "ok"
}
```

### Test 2 — asset coverage

```http
GET /api/v1/historian/FS-031/available-signals
```

Expected:

```text
liquid_rate
intake_pressure
discharge_pressure
motor_current
motor_temperature
...
```

### Test 3 — window

```http
GET /api/v1/historian/FS-031/window?... 
```

Verify:

```text
correct timestamps
correct values
correct asset
correct signal
correct unit
```

### Test 4 — aggregation

Compare:

```text
raw
1 minute
5 minute
15 minute
1 hour
```

### Test 5 — quality

Inject/check:

```text
missing samples
duplicate samples
stale samples
bad quality
out-of-order timestamps
```

### Test 6 — no-data period

Ask for:

```text
FS-031
2025-01-01 → 2025-01-02
```

Expected:

```text
empty / no coverage
```

not fabricated zeros.
