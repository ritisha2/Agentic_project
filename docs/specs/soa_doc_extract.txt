ESP APM ΓÇö SERVICE-ORIENTED ARCHITECTURE
LOGICAL SERVICES vs DEPLOYMENT PROCESSES ΓÇö IMPLEMENTATION STANDARD
Defines the production-grade approach for separating responsibilities without creating a microservice-per-component architecture. Companion to the Phase-5 REST + MCP service design.
1. Architecture Decision
Use logical service boundaries across the ESP APM platform. A logical service does not automatically become a separate process or container. A service becomes a separate deployable only when independent scaling, ownership, security, failure isolation, release cadence, or compute characteristics justify it.
This preserves the guideline's separation of Asset Context, Data Services, Engineering Services, Knowledge Services, ML Services, Digital Twin and Governance while avoiding unnecessary fragmentation. [Guidelines.pdf ┬º4.1ΓÇô┬º4.2]

28. Phase Mapping
29. MUST Rules
One business implementation per capability.
One canonical schema per domain contract.
Agent access only through tools/services.
REST is the default service interface.
MCP is selective and backed by the same application services.
External systems are isolated behind adapters.
Source of truth is explicit.
Security is enforced server-side.
Provenance/version/QoD is retained where applicable.
Logical service boundaries remain stable while deployment topology evolves.
30. MUST NOT Rules
One container per Python module.
Different business logic in REST and MCP.
Direct database access from Agents.
Direct Redis access from Agents.
Engineering formulas hidden in prompts as source of truth.
Frontend orchestration of every service call.
Services created merely to mirror tables.
Microservice deployment used as an objective.
