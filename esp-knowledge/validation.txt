Yes. This should be handled as a **Knowledge Quality / Validation layer**, not by simply assuming that uploaded documents are correct.

For your ESP Agent, there are actually **three different correctness problems**:

1. **Is the source document itself authoritative?**
2. **Was the information extracted and classified correctly?**
3. **Was the information converted into the right technical/semantic representation for the Agent?**

For the **Algorithm / ML part**, add a fourth:

4. **Does the KB description accurately represent what the actual model does?**

The ESP deck explicitly requires the system to be reproducible, versioned, explainable and testable, and it separates model runtime from the assistant.  

# 1. Think of KB correctness as a pipeline

```text
SOURCE
  ↓
DOCUMENT VALIDATION
  ↓
PARSING VALIDATION
  ↓
CLASSIFICATION VALIDATION
  ↓
STRUCTURED DATA VALIDATION
  ↓
SEMANTIC VALIDATION
  ↓
CROSS-SOURCE VALIDATION
  ↓
RETRIEVAL VALIDATION
  ↓
AGENT ANSWER VALIDATION
```

Do **not** wait until the Agent gives a wrong answer to discover that the KB was wrong.

---

# 2. Level 1 — Source correctness

Before putting anything into the KB, assign each source a trust level.

Example:

| Source                         | Authority   |
| ------------------------------ | ----------- |
| OEM ESP manual                 | Very high   |
| OEM pump datasheet             | Very high   |
| Approved client SOP            | Very high   |
| Internal engineering procedure | High        |
| Published technical paper      | Medium–High |
| Public website                 | Medium      |
| Unverified PDF                 | Low         |
| User-uploaded random document  | Unknown     |

Store:

```text id="h8kq74"
source_id
source_type
publisher
manufacturer
document_version
publication_date
approved
authority_level
```

Then your Agent can prefer higher-authority information.

# 3. Level 2 — Extraction correctness

Suppose your source says:

> Pump rated frequency = 60 Hz

Parser extracts:

```json id="qv4u24"
{
  "parameter": "frequency",
  "value": 60,
  "unit": "Hz"
}
```

You should automatically validate:

```text id="rbq10w"
Is value numeric?         ✓
Is unit valid?             ✓
Is parameter recognized?   ✓
Is range plausible?       ✓
Is source location known? ✓
```

If the parser extracted:

```text
frequency = 600
```

the system should flag:

```text id="xqbx5s"
OUTLIER / REVIEW REQUIRED
```

rather than embedding it.

---

# 4. Level 3 — Schema validation

Every structured KB object should have a schema.

For example, an algorithm definition:

```json id="ds5v3s"
{
  "algorithm_id": "xgboost_v1",
  "algorithm_family": "gradient_boosting",
  "purpose": "fault_classification",
  "input_type": "tabular_features",
  "supports_probability": true,
  "supports_sequence_data": false,
  "training_required": true,
  "version": "1.0"
}
```

Validate with:

* JSON Schema
* Pydantic
* SQL constraints
* enum validation
* type checking

If someone enters:

```text id="x76q4w"
supports_probability = "yes"
```

your ingestion pipeline rejects it.

---

# 5. Level 4 — Semantic validation

This is the important one for your **Algorithm / ML Knowledge** category.

A document might say:

> XGBoost is used for fault classification.

That is not enough.

Your KB record should define what that means **in your system**.

Example:

```text id="n0g52y"
MODEL:
Fault Classifier v1.4

PURPOSE:
ESP fault classification

INPUT:
Engineered ESP telemetry features

OUTPUT:
fault_class
confidence

CLASSES:
GAS_INTERFERENCE
STAGE_WEAR
...
```

Now validate:

```text id="8g84ny"
Does actual model output contain fault_class?      ✓
Does actual model output contain confidence?       ✓
Are listed classes valid?                         ✓
Does the model actually support those classes?   ✓
```

This prevents the KB from saying something that the actual model does not do.

# 7. Build a "Model Contract Test"

This is probably the most useful thing for your situation.

Suppose your AI team says:

```text
GET /models/ESP-001/prediction
```

returns:

```json id="mxb5ri"
{
  "asset_id": "ESP-001",
  "failure_risk_24h": 0.31,
  "rul_hours": 96
}
```

Your test automatically checks:

```text id="d41ibd"
KB says:
failure_risk_24h → numeric probability
RUL → hours

Actual API:
failure_risk_24h → numeric ✓
RUL → hours ✓
```

If tomorrow their team changes:

```text
rul_hours
```

to:

```text
rul_days
```

the contract test fails.

That is much better than allowing the Agent to silently misinterpret it.

# 9. Validate numerical semantics

This is another common failure.

Suppose KB says:

```text id="2hfpaa"
failure_risk_24h = 0.72
```

Is that:

* 72% probability?
* normalized risk score?
* anomaly score?
* severity?

Your KB needs explicit semantics:

```text id="e5i5ck"
field: failure_risk_24h

type: probability

range: 0–1

display:
0.72 → 72%

horizon:
24 hours

meaning:
predicted probability of configured event within 24h
```

Without this, an LLM can misinterpret the field.

For ESP knowledge, this is essential.

Store:

```text id="6trg0l"

canonical_unit
accepted_units
conversion
range
domain
```

Example:

```text
motor_temperature

canonical:
°C

accepted:
°F
°C

conversion:
°F → °C

plausible range:
0–250°C
```

Then validate every ingestion.

# 11. Cross-source validation

This is where your KB becomes much more reliable.

Example:

### Source A

OEM manual:

```text
Motor max operating temperature = X
```

### Source B

Client engineering configuration:

```text
ESP-007 temperature limit = Y
```

### Source C

Model configuration:

```text
thermal threshold = Z
```

Now the system should detect:

```text id="7gkdzi"
A ≠ B ≠ C
```

and raise:

```text
KNOWLEDGE CONFLICT
```

Do not silently choose one.

The Agent should know:

> There are conflicting values and engineering review is required.

## The core principle

**Never treat "data exists in the KB" as "data is correct."**

For your Agent, a KB entry should move through:

```text id="h4g5yq"
INGESTED
   ↓
STRUCTURALLY VALID
   ↓
SEMANTICALLY VALID
   ↓
SOURCE VERIFIED
   ↓
CROSS-CHECKED
   ↓
APPROVED
   ↓
PUBLISHED
```

And for **Algorithm/ML knowledge**, the final authority should be:

> **actual model contract/API + model registry + approved model documentation**

not simply whatever someone typed into the KB.

That is particularly important in your case because **the ML models belong to another team**. Your Agent needs to consume their outputs correctly without pretending it understands model internals that were never formally specified. The ESP deck itself defines model runtime separately from the assistant and requires reproducibility/versioning and traceability.
